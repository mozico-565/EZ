# Protocol security and threat boundaries

Fresh ephemeral P-256 keys + random32-byte nonces per connection. Length-prefixed protocol version, roles, public keys, nonces and bounded display names form role-ordered transcript. ECDH secret, transcript SHA-256 salt and HMAC-SHA256 extraction/expansion derive independent directional AES256 keys and six-digit SAS. Each AES-GCM record has monotonic64-bit sequence in a12-byte nonce, fixed protocol/sequence AAD,16-byte authentication tag, bounded ciphertext length. Keys never reused across connections. No file content is sent before local sender confirmation AND remote receiver approval. Users MUST compare SAS on both phones. Names/IPs alone are untrusted.

SAS is a manual verification mechanism, not account authentication or audited security. A six-digit code has limited entropy and requires user attention; no silent trust, persistent trust or automatic approval. One receiver connection at a time, metadata bounds, 16GiB cap and30-second inactivity timeout reduce resource exposure; approval allows120seconds. Metadata itself is visible to the selected encrypted peer before final approval. Authentication of the peer depends on the manual comparison.

SHA-256 verifies full received stream against sender's terminal hash and announced length. Receiver closes output, re-reads saved bytes through SAF to check the stored SHA-256, renames the partial document, then returns count+hash receipt; sender only marks success on that receipt. Integrity failure calls best-effort abort/delete, no success. SHA does not replace pairing or encryption. No release security claim; independent protocol review, fuzzing, malformed EC keys, downgrade/replay testing, DoS analysis and physical devices remain required.

Report any SAS mismatch, unexpected acceptance, data corruption, unwanted overwrite or leaked plaintext. Do not use for sensitive production files until reviewed and device tested.


## Protocol2 release work

Protocol2 uses the same bounded ECDH/AES-GCM/SAS primitive with a distinct handshake magic/transcript domain and an encrypted bounded manifest (1..256files, encoded <=65537bytes, each file <=16GiB). Protocol1 tests are retained unchanged; incompatible peers fail closed. File bytes wait for both approvals. The approved manifest names/count/size are displayed on confirmation. Each file independently verifies stream length/hash, closes the destination, verifies stored bytes, publishes, and returns a hash receipt. Earlier verified files are retained if a later file fails. Cleanup failure is surfaced; do not call a partial successful. Filename sanitization/duplicate handling remain receiver-side.

QR payload is bounded to512chars, version2/ezpair only, numeric private/link-local IPv4 and port1024..65535, exact known fields, a32hex session nonce and at most600second lifetime. No URL navigation/DNS/internet endpoint is accepted. Nonce is checked against the live receiver before approval; SAS still authenticates manually. Camera analysis is local ZXing, with bounded frames and row/pixel stride handling; no ML/GMS model or mandatory cloud service. Metadata and nonce are not long-lived secrets. Local clients can still cause denial of service or user prompt spam; do not infer identity from names.

APK export is limited to an installed known single-package APK and verifies copied package/version/certificate before sharing. FileProvider exposes only its dedicated export cache, grants read-only URI access and no prefix/write/broad private-file exposure. The app does not silently install apps. APK installability and actual receiving permission across apps require physical tests.

Release gate checks the exact signed candidate hash, source fingerprint, expected certificate, workflow provenance, explicit approved commit and all physical results; unsigned/debug or missing evidence blocks publication. No production key is generated ephemerally or committed. Independent cryptographic audit and fuzz/DoS review remain valuable and have not been falsely claimed.
